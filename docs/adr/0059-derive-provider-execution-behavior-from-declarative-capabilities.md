# Derive provider execution behavior from declarative capabilities

Generic publish paths — command assembly, working-directory resolution, default output derivation, output preflight access, project publish profile sources, solution recommendation, and command import — must read declarative provider capabilities and discovery data instead of branching on provider identity or a provider type enum, because ADR-0024 already made declarations the composition contract and every identity branch re-created a Tauri/dotnet special case the composer was written to prevent. Providers keep their knowledge in one place (provider implementation, versioned schema, and declarative capability fields, with schema `defaults` and flag `aliases` closing the gap ADR-0030 already required); genuinely behavioral logic that cannot be data, such as Gradle wrapper detection, stays as a finite strategy enum chosen by declaration. Data-driven provider manifests — replacing provider source files with pure data files — are deliberately deferred: with only the built-in providers as consumers the manifest format would be shaped by dotnet's shadow, so the introduction of the next new provider must first decide whether to introduce that format (per ADR-0025, external plugin loading stays out of scope until a real ecosystem exists). Adapter conformance (ADR-0053) verifies capability truthfulness, including that schema-derived command import and rendered commands match declared behavior.

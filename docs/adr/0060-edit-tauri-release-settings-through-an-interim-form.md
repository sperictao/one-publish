# Edit Tauri release settings through an interim form

Until the schema-driven editor of ADR-0030 can express Tauri release settings, the publish-configuration module offers a dedicated release-settings form for Tauri configurations, reachable from the configuration row and from the automation binding dialog; this amends ADR-0058's rule that the settings stay read-only in the UI. The form edits every `TauriReleaseConfig` field except the system-managed `managedWorkflowVersion`; when the current revision has no settings it starts from the defaults refined by inspecting the bound project (configuration path, app name, build driver, version-mirror suggestions), but nothing is written until the user saves, so creating a configuration never invents settings and unsigned releases still need the explicit authorization of ADR-0006. Saving runs `validate_release_config` in the backend before persisting a new immutable revision under the reserved `releaseSettings` key, and any update that supplies changed settings passes the same gate, while ADR-0058's inheritance — an omitted key inherits, an explicit `null` clears, a provider switch drops — is unchanged. The form is a scoped exception to ADR-0030's rule that adapters do not own configuration pages: it covers only this reserved key, lives in the shared configuration module, and is deleted when release settings migrate to per-adapter schemas. Configuration backups keep stripping secret-name fields under the existing sensitive-key policy, so imported settings parse without them and must be completed in the form before automation can bind, consistent with ADR-0003.
